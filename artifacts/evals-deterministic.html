02

Findings

The typo-propagation defect is resolved

resolved

Q02 and Q10 both now correctly state 150mm/200mm for the two 1.4mm guidepins, sourced from the graph's Part record rather than the OCR-damaged PDF chunk that reads "50mm." This was the most reliably reproducing defect in the whole review (5 of 6 chances across three prior runs) — graph-grounding fixed it exactly as ticket 20 predicted.

One caveat: Q04 (a third phrasing of the same fact) still said "50mm" despite correct catalog facts being right there in its own context — a generation-level misread, not a missing-data problem (verified by reading the actual prompt input: the aggregated facts block correctly said 150mm). Isolated, not systematic — 2 of 3 same-fact questions this run got it right.

The FT/PT screw mixup is still open — but the root cause is no longer a guess

open

Q05 still calls the bunion procedure's 4.0mm/3.5mm screws "MIS PT Screw" when the graph says thread: "Full". Traced directly: the procedural path's term extraction only ever reads reranked passage text, and the Full-Thread screw inventory chunk isn't reliably in that top-5 for this query — so resolve_skus never sees an MSCF... token to resolve, no matter how good the resolution mechanism itself is.

Likely fix, not implemented: also extract terms from the raw query for the procedural path — it literally says "a 4.0 and 3.5 screw for their bunion." A small follow-up, not a new ticket.

Fixing the judge's blind spot was required, not optional

found mid-implementation

self_eval only ever judged the draft answer against reranked vector passages — never aggregated_facts. The first post-ticket-22 run showed exactly why that's broken: Q10's newly-correct "150mm" scored 0.0 faithfulness, because the judge only had the OCR-damaged passage (still "50mm") to check it against. The judge was penalizing the fix ticket 20 exists to make. Fixed by passing a synthesized catalog-facts passage into judge_answer alongside the real ones.

Why it matters: without this, every future graph-grounded correction would keep scoring as a regression, triggering pointless retries and actively misleading anyone reading the score instead of the answer.

A broad match can crowd out a complete one

found, partially addressed

Q01's first post-ticket run got noticeably worse (faithfulness 0.0) than the pre-ticket baseline: a generic term like "screw" matches far more real parts than any small limit can represent, so resolve_skus handed generate an arbitrary 5-part slice instead of the full range. Raised the per-term limit (5→10) and reframed the prompt so catalog facts read as a cross-check for named items, not a competing "complete" listing when the passage already has one full inventory table.

Net effect: content is now the most complete it's ever been (correctly covers both FT and PT across all three diameters), but the format regressed from range-compressed to fully enumerated — the added "known catalog facts" instructions likely diluted the earlier range-compression instruction's weight in an already-long system prompt. A real, observed tradeoff, not fully resolved.

SKU-recall instability and the missing SKU-redirect both look resolved

resolved

Q06/Q07 (the SKU lookups that flipped between correct and "not found" across earlier runs, purely on vector-rerank luck) are now deterministic — a direct graph lookup, not a chance draw. Q08 (asking about a nonexistent 1.5mm wire) now proactively lists the real 1.2mm/1.4mm/1.6mm alternatives with SKUs, instead of stopping at "not found."

03

Bugs a direct-testing loop caught before they shipped

Every one of these would have shipped silently on faith in the design alone — each was only found by actually running the code against the real graph DB or a real eval pass and reading the output, not by inspection.

find_parts returned a nested shape the caller didn't expect

{"part": {...}, "product_family": ...} instead of a flat dict — so part.get("sku") was always None and every single match was silently dropped. Caught by a direct smoke test before the first real eval run, not by the eval itself.

A plural query term never matches a singular catalog entry

"guidepins"/"wires" as typed never substring-match "GUIDEPIN"/Term-node "wire" as stored. Added a crude trailing-s-strip (with_singular_variants), shared between resolve_synonyms and resolve_skus — and initially applied it to only one of the two, missing the exact case ("wires" → "guidepin" via synonym) it was meant to fix. Caught by testing the "wires" phrasing specifically, not just the "guidepins" one that happened to work already.

The classifier put the word "null" where it meant to leave a field empty

Structured output occasionally set system to the literal string "null" instead of an actual null value, which then scoped the graph lookup to a nonexistent ProductFamily named "null" — silently zeroing out graph-grounding for the whole turn. Caught by noticing resolved_parts: [] on a question that should have matched, then tracing it back through the actual trace data.
