Findings

deterministic's pipeline nodes were quietly protecting the agent's tools from their own gaps

found, all fixed

Three real bugs, each caught by watching what the agent actually chose to pass a tool, not by inspection:

Q04, first pass — called synonym_resolve(term="guidepins") (plural) and got [] back, because the graph's Term node is singular ("guidepin"). deterministic.py's resolve_synonyms node already singularized before calling this same tool — the tool itself never did.

Q02, first pass — called part_lookup(term="1.4 guidepin", product_family="MIS - Foot Recon") and got [] back: the family name needed to be "MIS", and the compound phrase never substring-matches a compound catalog description either.

Fixed at the tool layer (find_parts, synonym_resolve), not the agent's prompt — deterministic.py's own resolve_skus/resolve_synonyms nodes get the same benefit going forward, and any future caller does too.

The judge didn't know about the inline-citation convention either

found, fixed

judge_answer's own system prompt only described bracketed [doc-id#n] citations as valid -- so an answer built entirely from part_lookup (correctly citing inline per both workflows' own generate prompts, exactly as designed) scored a hard 0 on the citation axis regardless of how well-grounded it actually was. This under-scored several genuinely good answers in the first pass. Fixed by telling the judge about the convention directly.

Once the tools were fixed, the agent matched deterministic at a fraction of the cost

the headline result

8 good / 2 partial / 1 miss here vs. deterministic's 7 good / 3 partial / 1 miss — roughly on par, arguably slightly ahead. The gap is in how they get there: this run averaged 2.5 tool calls per question (min 1, max 4), where deterministic's fixed pipeline always runs its full sequence regardless of question difficulty — hybrid_retrieve, rerank, and resolve_skus alone can issue dozens of Neo4j lookups in a single turn (up to MAX_TERMS_PER_TURN=40 candidate terms). The agent asks exactly as many questions as it needs.

What this means for the ticket 22 vs. 23 question: the grilling session's premise -- that the concrete need described didn't require model-decided control flow -- still holds; nothing here needed the agent to invent a new strategy. But "fixed pipeline is strictly cheaper for the same quality" turned out to be false once the tools were equally good -- the agent got the same quality for less work.

The FT/PT thread-type mixup is architecture-independent

open, confirmed cross-architecture

Q05's back-table answer is the richest, most organized version of this answer across every run of either workflow -- and still labels the primary bunion implant "Compression PT" (Partial Thread) when the graph's own record says thread: "Full". Same failure, same question, in a completely different reasoning architecture with completely different tool-call sequencing.

Why it matters: this rules out "the pipeline structure is the problem." Neither workflow reliably ties a procedure's intent (bunion = Full Thread) to the right implant without being told that relationship explicitly -- it's not in either the catalog properties or the retrieved prose in a form either architecture reliably picks up. A real, deeper grounding gap, not a routing or tool-choice one.

The one remaining miss shows the agent is less consistent turn-to-turn than the fixed pipeline

residual difference

Q03 ("wires: top vs. bottom") and Q04 ("guidepins: top vs. bottom") ask the same underlying fact two different ways. Q04 answered it correctly (material: CoCr/Stainless top, Titanium bottom). Q03, phrased with "wires," went looking through guidepin SKUs directly and produced a confused, badly-structured answer that doesn't match Q04's. deterministic's fixed resolve-then-aggregate mechanism runs the identical procedure regardless of phrasing, which makes it inherently more consistent turn-to-turn than an agent whose reasoning path can diverge based on which words point it toward which tool first.
