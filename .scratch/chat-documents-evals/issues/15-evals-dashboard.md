# 15: Eval tab -- flagged-feedback rerun tool

**What to build (rescoped 2026-09-05, grilling session):** the original idea here -- a golden-dataset CI harness with run-history persistence -- was blocked on ticket 13, which was itself shelved the same day once every workflow's clarification-pause behavior undermined its premise (see ticket 13's file for why). This ticket became something smaller and more immediately useful instead: an admin-only `/evals` page ("Eval tab") that lists flagged feedback and lets an admin re-run a flagged question against the current code, in its real conversational context, to check whether a fix actually worked.

**Blocked by:** 01 (Postgres migration tooling), 02 (Email/password auth with admin flag), 11 (Chat inline per-message 4-axis feedback). No longer blocked by 13.

**Status:** done (2026-09-05), verified live via a real 3-role browser flow (Playwright: a rep asks a real question and flags the answer, a freshly-signed-up admin is promoted via a direct DB flip, visits `/evals`, sees the flagged item with its real question/answer text, triggers a rerun that streams a fresh live answer with a working feedback control, toggles the item resolved and confirms it survives a full page reload, and confirms the rerun shows up in that item's history after reload) -- not just unit tests, though `backend/tests/test_feedback_routes.py`/`test_chat_routes.py` also gained real integration coverage (29 new/changed test cases, real Postgres/LLM, no mocking).

## Design (settled via grilling, in order of the decisions made)

1. **Scope**: only feedback rows with `flagged: true` show up -- an explicit human signal, not a score-threshold heuristic. No filters/sorting beyond newest-first for v1.
2. **Replay shape**: a rerun replays the *full* conversation up to (not including) the flagged question, then re-asks that exact question fresh -- not an isolated single-turn rerun. Implemented via `graph.aupdate_state` seeding the new thread's history with the original message objects verbatim (verified live: their original ids are preserved, not reassigned, while the fresh turn's own new messages get real new ids) -- far cheaper and more exact than re-running every prior turn through a live LLM call.
3. **Batching**: one item rerun at a time, not a batch/report -- batch reintroduces most of the complexity this ticket was trying to avoid by not being ticket 13.
4. **Clarification during a rerun**: surfaces live and an admin answers it in the moment (the same `interrupt()`/resume mechanic every workflow already has), never auto-replayed from the original answer -- the whole point is watching the *current* code decide fresh.
5. **Workflow choice**: an admin picks which registered, functional workflow to rerun against (defaulting to the original), reusing the existing `GET /admin/settings` workflow list (ticket 14) -- not locked to whatever the original conversation happened to use.
6. **Persistence & where it lives**: a rerun is persisted as a genuine new `chat_threads` row (not a separate `reruns` table -- see "Implementation" below for why that simplification held up), nested under its flagged item's card, kept forever (never overwritten) so re-running after a fix doesn't erase the record of what happened before it. Reruns are visible ONLY on the Eval tab, nested under the flagged item -- never in an admin's own personal chat sidebar.
7. **Item list scope**: unfiltered by `resolved` -- a resolved item stays visible (with its rerun history intact) rather than disappearing, so the admin toggles it in the UI rather than the list silently hiding it.
8. **Scoring**: no separate scoring step -- a rerun is a real turn through the real graph, so `self_eval` already produces `eval_scores` as part of running it at all; shown via the same `MessageFeedback` control every real chat answer gets, not a bespoke comparison UI.
9. **Display**: reuses the actual chat UI (streaming bubbles, citation chips, the feedback control) rather than a stripped-down summary row or a "kick off -> spinner -> result" pattern -- an admin reviewing a flagged item is meant to see exactly what a rep would have seen.
10. **Resolution tracking**: a separate `resolved` boolean on `feedback`, toggled independently of `flagged` (which stays a permanent record that someone complained) -- lets the list actually shrink to what's still outstanding.

## Implementation notes (for whoever reads this later)

- **A rerun didn't need its own table.** The original round-2 design sketch proposed a dedicated `reruns` table; once "reuse the actual chat UI" (decision 9) was settled, it became clear a rerun IS a real `chat_threads` row like any other -- it goes through the identical graph/checkpointer/streaming machinery, so `GET /chat/threads/{id}` and `POST /{workflow_name}/resume` work on it completely unchanged with zero new read paths. `chat_threads` gained two nullable columns instead: `rerun_of_message_id` (FK to `feedback.message_id`, null for every ordinary thread) marks and links a rerun; `workflow_name` records the explicit choice so a later resume call routes to the right graph. `list_threads` (the personal sidebar) excludes non-null `rerun_of_message_id` rows; a new `list_reruns(message_id)` is the inverse query. Migration: `0bb3fb27c761`.
- **New backend surface**: `feedback.resolved` column + `ResolvedRequest`/`FlaggedFeedbackOut` models; `GET /feedback/flagged` (question/answer text read live from the checkpointer, same source of truth `GET /chat/threads/{id}` uses -- never duplicated into the `feedback` table itself), `PATCH /feedback/{message_id}/resolved`, `GET /feedback/{message_id}/reruns` (all in `feedback.py`, admin-gated); `POST /chat/rerun` (`chat.py`, admin-gated, does the history-seeding + streams via the existing `_stream_graph`).
- **New frontend surface**: `app/evals/page.tsx` (the Eval tab, linked from nav already -- it existed as a dead link before this ticket), `app/evals/flagged-item.tsx`, `app/evals/rerun-conversation.tsx` (the embedded live/history chat view), `lib/feedback/{types,api}.ts`. `lib/chat/format.ts` was extracted from `app/chat/page.tsx` (status labels, citation-marker stripping, citation chip labeling) so the rerun view and the main chat page can't silently drift apart on what a chat turn looks like.
- **A real bug found live, unrelated to this ticket's own code**: the disposable `postgres-test`/`neo4j-test` containers (`tests/conftest.py`) accumulate orphaned `systems`/`documents` rows across repeated local `pytest` invocations whenever a test fails before reaching its own cleanup step -- this made unrelated `test_chat_routes.py` tests intermittently fail with a missing "done" event (a spurious `detect_intent` system-disambiguation pause) purely from accumulated test-fixture noise, not a real regression. Fixed each time by `docker compose --profile test down postgres-test neo4j-test && docker compose --profile test up -d postgres-test neo4j-test` (safe -- these containers are explicitly disposable fixture-only data). Recurred multiple times this session; worth remembering if this happens again.
